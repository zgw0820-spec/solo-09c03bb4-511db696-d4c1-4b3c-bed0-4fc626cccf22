# 边缘网关值班切换 Demo

FastAPI + SQLite 实现的边缘网关与操作网页。值班员切换处理较久的 HTTP 服务上游时，
已接纳的请求仍从原上游取回完整响应；新请求在确认切换后立即走新目标。
每个上游有 1～5 个并发名额，慢请求占满名额时超额请求排队等候（最多 5 秒），
超时返回“忙碌”且不转发。

## 组成

| 组件 | 说明 |
| --- | --- |
| `gateway/` | FastAPI 网关：名额管控转发、操作 API、值班台网页（`/`）、SQLite 持久化 |
| `upstream/` | 演示上游：可设默认响应延迟（`DEFAULT_DELAY_MS`），请求参数 `delay_ms` 可覆盖；`/health` 供切换前探测 |
| `docker-compose.yml` | 一键启动网关 + 两个本地上游（alpha 默认 3s、beta 默认 0.5s） |
| `scripts/` | 本地（无 Docker）端到端验证脚本 |

## 运行

Docker Compose：

```bash
docker compose up --build
# 值班台网页: http://localhost:8080/
```

本地直接跑（无需 Docker，含自动化断言与重启演练）：

```bash
./scripts/run_local.sh
```

## 网页演示建议

1. 打开 http://localhost:8080/ ，把当前目标（alpha）的名额下拉框改为 **1**。
2. 延迟填 `3000`，点“并发 N 个”（N 默认 5）：表格里看到 alpha **在途 1、等候 4**，
   约 5 秒后等候中的请求陆续记为橙色“忙碌（未转发）”。
3. 再发一批并发请求，趁有请求等候时“探测候选 → 确认切换”到 beta：
   等候者立即改向 beta 争取名额并由 beta 返回；已在途的慢请求仍从 alpha 取回响应，
   alpha 行显示“排空中”，在途清零后才显示“可下线 ✓”。
4. 把名额调小（如 3→1）观察：在途请求不被打断，但在途降回名额以下之前不再接纳新请求。

## 语义与实现要点

### 并发名额

- **每目标 1～5 个名额**：网页下拉框或 `POST /api/upstreams/{name}/capacity` 调整，
  边界（0、6）与未知目标会被拒绝（422/404）。名额是配置，持久化在 SQLite，重启保留。
- **取得名额才登记在途**：`db.try_admit` 在同一临界区内完成“快照当前路由 →
  检查该目标在途 < 名额 → 登记在途（占用名额）”，因此名额修改、请求接纳与
  切换交错时不会超配，也不会把请求钉到已切换的旧目标上。
- **超额等候，最多 5 秒**：名额占满的请求进入内存等候表（`WAIT_TIMEOUT_SECONDS`，
  默认 5s），每 50ms 重试一次接纳；超时返回 `503 {"error": "busy"}`，**不转发**，
  等候记录随即删除，不留占位。
- **等待期间确认切换 → 立即改向新目标争取**：等候者每次重试都重新读取当前路由，
  切换提交后下一个重试周期（≤50ms）即转向新目标竞争名额；已接纳（已占名额）的
  请求不受切换影响，仍从原目标取回完整响应。
- **调低名额不打断在途**：名额调低只影响后续接纳；在途数可以暂时高于新名额，
  期间不再接纳新请求，直到在途降回名额以下。旧目标是否可下线仍只看在途是否清零，
  不因名额调低或路由切走而提前提示。
- **超时与重启不留占位**：等候记录只存内存，超时即删；`inflight` 表（名额占用）
  在启动时清空，被 kill 的进程不会留下占着名额的“幽灵”在途记录。

### 值班切换（原有语义）

- **已接纳请求走原上游**：接纳时原子快照路由并登记在途，随后无论路由如何切换，
  都从快照目标取回完整响应。
- **先探测后确认**：`POST /api/switch/probe` 只探测候选（`/health` + `/work`），
  从不改写路由；`POST /api/switch/commit` 才把路由切到新目标。
- **立即生效**：确认切换只做一次版本守卫的单行 `UPDATE`，不等待旧请求结束。
- **可下线提示**：非当前目标的在途数清零时，状态接口给出 `can_offline: true`。
- **版号防交错**：确认切换按 `version = base_version` 做比较并交换（CAS），
  迟到的确认收到 `409 version_conflict`，不得覆盖已生效路由。
- **重启恢复**：路由与上游登记（含名额）持久化在 SQLite；启动时清空 `inflight`
  表（清理条数在网页顶部展示）。

## 操作 API

| 方法/路径 | 说明 |
| --- | --- |
| `GET /api/state` | 当前路由（目标+版号）、各上游名额/在途/等候数、在途与等候明细、最近探测 |
| `POST /api/call` | 发起转发请求 `{delay_ms?, path?}`；名额满时最多等候 5s，超时返回 503 `busy` 且不转发 |
| `POST /api/upstreams/{name}/capacity` | 设置该上游名额 `{capacity: 1..5}`；未知目标 404，越界 422 |
| `POST /api/switch/probe` | 探测候选 `{target, base_version}`，不改路由 |
| `POST /api/switch/commit` | 确认切换 `{target, base_version, probe_id}`，版号冲突返回 409 |

## 验证

`scripts/run_local.sh` 启动两个上游与网关，执行 `scripts/smoke_test.py`
两阶段共 69 项断言：切换语义、探测失败维持路由、交错切换版号冲突、
慢请求从原上游取回完整响应、在途清零才可下线、名额边界校验、
名额占满时等候 5s 超时返回忙碌且不转发、等候期间切换立即转向新目标、
调低名额不打断在途且不再接纳、名额/接纳/切换交错全程不超配无错投、
`kill -9` 后重启的在途清理、名额配置保留与路由保持。
